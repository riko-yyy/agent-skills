# 要素・関連・プロトコルでキャッチアップする

どんな対象も、次の3つで捉えると理解しやすい。

- **要素**：実行主体（何かをするもの）と、リソース（されるもの・使われるもの）
- **関連**：要素同士のつながり。向きと種類を持つ
- **プロトコル**：その相互作用のルール。何を渡し、何を前提とし、失敗したらどうなるか

この Skill は、コード・Claude plugin・文書だけのリポジトリ・パイプライン・組織などを、この3つに分解して図と説明にする手順。目的は「全部を説明すること」ではなく、**何をどの順で読めば頭に入るか**を示すこと。読み手は初めてその対象に触る人なので、網羅より見通しを、断定より根拠を優先する。

プロトコルを中心に置く理由：要素の内側は後から読めばよいが、要素同士のルールを知らないと、どこを触ると何が壊れるかが読めない。キャッチアップで最初に効くのはプロトコル。

## 対象ごとの読み替え

対象の種類によって、何が実行主体で何がリソースか、どんなプロトコルがあるかが変わる。手順1で対象の種類を見極めたら、`references/lenses.md` の該当する節を読む（コード / Claude plugin・エージェント構成 / 文書だけ / パイプライン・CI / 組織・業務）。複数の種類が混ざっている場合は、該当する節をすべて読む。

## 手順

### 1. 範囲・種類・ズームレベルを決める
- 対象の範囲（リポジトリ全体、特定ディレクトリ、文書セットなど）と、種類（上の読み替えのどれか）を決める
- メインの図に出す要素は **7個前後、多くても10個まで**。人が一度に見渡せる数に収めるため。範囲の外にある要素（外部サービス、ブラウザAPI、GitHubの設定など）も数に含める。多いときは上位の要素でまとめ、細部は「ズームイン候補」として残す

### 2. 要素を出す
- **実行主体**：自分から動くもの。処理、ジョブ、エージェント、hook、人、チーム
- **リソース**：動かされる・読まれる・書かれるもの。データ、ファイル、文書、設定、テーブル、成果物（PRなど実行時に生まれるものも含む）
- 1つのものが両方の顔を持つときは、この対象での主な役割で決める（例：skill の SKILL.md は、読み込まれるリソースとして扱う）
- **人も実行主体になる**。依頼する・承認する・書く・判断するなど、対象の中で役割を持つ人は、ほかの実行主体と同じように要素として描く。「対象外」の見た目にするのは、範囲の外にあるものだけ
- 各要素に **責務を1行** で付け、根拠（ファイルパスや文書名）を添える

### 3. 関連を出す
向きつきで列挙し、種類を付ける。種類は要素の組み合わせからほぼ決まる。

| from → to | 関連の種類（例） |
|---|---|
| 実行主体 → 実行主体 | 起動する、呼び出す、依頼する、イベントで発火させる |
| 実行主体 → リソース | 読む、書く、生成する、更新する |
| リソース → リソース | 参照する、前提にする、上書きする（どちらが優先か） |

循環や双方向のつながりがあれば明記する。

### 4. プロトコルを出す
関連ごとに次を書く：
- **何を渡すか**（型、メッセージ、イベント、ファイル、用語）
- **前提**（事前条件、順序、権限、どちらが正か）
- **失敗時**（例外、リトライ、補償、放置、気づけない）
- **強さ**：ルールがどこまで守られる仕組みになっているか。3段階で判定する
  - **強制**：仕組みで守られる。型、スキーマ、テスト、権限設定、CIのチェック、hookによるブロック。根拠を `path:line` で示す
  - **記述**：書かれているが、守らなくても何も止まらない。README、コメント、プロンプトや SKILL.md の指示、規約。根拠を `path:line` で示す。また、コードはそう動いているがルールとしてはどこにも書かれていないものもここに入れ、「実装のみ」と添える
  - **暗黙**：どこにも書かれておらず、動作からも確かめられない。推測で埋めると読み手が誤ったモデルを持つので、暗黙のまま残す
- 強さは関連の両端で違うことがある（例：書く側はコードで形式を守るが、読む側は形式が違っても警告だけで通す）。その場合は「書く側：強制／読む側：記述」のように分けて書く
- 範囲を絞ったせいで確かめていないもの（読まなかったコードとの対応など）は、暗黙ではなく **未確認（範囲外）** と書く。暗黙は「確かめたが、どこにも無い」ものに限る

### 5. ずれと重複を出す
- **ずれ**：同じことについて、2つの場所で言っていることが違う箇所。設計図と実装、README と設定、文書Aと文書B、テンプレートと実際の動き、などがある。どちらが正しいかを判断できないときは、判断せずに両方を示す
- **重複**：同じルールや判断が複数の場所に書かれていて、どれが正本か決まっていない箇所。今は一致していても、片方だけ直されるとずれになる

どちらも、キャッチアップする人が最初につまずく場所なので独立した項目にする。

### 6. 確認することリストを作る
「暗黙」と「ずれ」を、具体的な質問にする。
- 例：「OrderService が InventoryAPI を呼んで失敗したとき、注文は取り消されるのか保留なのか？」
- 聞く相手がいない対象（個人開発など）では、「決めることリスト」として書く。決めたら、どこに書き残すとよいかも添える

### 7. 読む順番を出す
- 原則：**プロトコル → 要素の責務 → 内側の実装・詳細**の順
  - 先に読むもの：README・概要、インタフェース、型定義、スキーマ、設定、テスト、用語の定義
  - 後に回すもの：要素の内側の実装や本文
- 具体的なファイル・文書名を、順番つきで5〜10件挙げ、それぞれ「なぜここで読むか」を一言添える
- 図の箱に対応するものは、箱に丸数字を振る。箱にならないもの（README、型定義など）は、図の下に「図の外で先に読むもの」として並べる

### 8. 理解を確かめる問いを出す
「この要素を差し替えたら何が壊れる？」「このルールを破ったら何が起きる？」形式の問いを3つ程度。文書が対象なら「この文書を書き換えたら、どの文書が古くなる？」の形にする。答えられればメンタルモデルができている、という自己チェックに使う。

## 出力形式

**図（SVG）＋説明**を基本とする。

- **デフォルト**：自己完結した1枚のHTMLファイル（SVGをインラインで埋め込み、説明を同じページに書く）。ファイル名は `ERP.html`
- **リポジトリに置く場合やユーザーが求めた場合**：`ERP.svg` ＋ `ERP.md`（mdから相対パスでsvgを参照する）

### メインの図
要素・関連・プロトコルを1枚に描いた、全体を見渡すための図。

- **実行主体は角丸の箱、リソースは書類や円柱など別の形**にする。形で区別すると、矢印の意味（動かす／読む・書く／参照する）が読み取りやすくなる
- 箱の中は名前と責務1行（3行以内）
- 関連 = 矢印。ラベル = プロトコル名（例：`POST /orders`, `find / save`, `on: pull_request closed`, `description で発動`）。関数ならシグネチャを短く書く
- 関連の種類で線を変えたいときは、太さや矢じりで分ける（例：起動・呼び出しは太線、読む・書くは細線）。凡例に書く
- **強さで線種と色を分ける**：強制 = 青の実線、記述 = 青の点線、暗黙 = 橙の破線。強い関連に付随する暗黙の前提は、その矢印の近くに橙の短い注記で書く
- ズームイン候補は二重枠、範囲の外にあるもの（外部サービス・未実装・別リポジトリ）は灰色の破線枠
- **凡例を必ず図の中に入れる**。図は説明から切り離されて共有されることが多く、凡例がないと線や形の意味が伝わらない
- **フォントはゴシック体を指定する**。指定しないと環境によって明朝体で描画され、小さい文字が読みにくくなる。例：`font-family="'Noto Sans CJK JP','Hiragino Sans','Yu Gothic','Meiryo',sans-serif"`
- 色は意味のあるもの（強さ・対象外）だけに使い、装飾に使わない
- **図に書くのは名前・責務1行・プロトコル名・短い注記まで**。ルールの一覧、エラーコードの一覧、根拠の行番号などは説明側の表に回す。図に文字を詰めると、見渡すための図が読むための図になり、スマホでは判読できなくなる
- 描いたら一度ラスタライズして目視し（`rsvg-convert` やヘッドレスブラウザが使えれば）、ラベルの重なりや見切れを直す

### 補助図（任意）
メインの図だけでは伝わりにくいものがあれば、1〜2枚まで足してよい。例：状態遷移、処理やイベントの流れ（シーケンス）、境界値、ファイル×実行主体の読み書き表（どの主体がどのファイルを読む・書くか）。どのプロトコルを詳しく見るための図かを見出しで示す。svg+md形式なら別ファイル（`ERP-<内容>.svg`）にする。

### 説明のセクション構成
1. **ひとことで**：この対象が何をしているかを2〜3文で
2. **要素表**：要素 / 実行主体かリソースか / 責務 / 根拠
3. **関連とプロトコル表**：from → to / 関連の種類 / 何を渡すか / 前提 / 失敗時 / 強さ（根拠）
4. **ずれと重複**：どこと、どこが、どう食い違っているか／同じことがどこに重ねて書かれているか
5. **読む順番**：番号つきリスト
6. **確認することリスト**（または決めることリスト）
7. **理解チェック**
8. **ズームイン候補**

## 注意
- 根拠を示せないことを断定しない。わからない箇所は「暗黙」か「不明」と書き、確認することリストに回す
- 網羅より見通しを優先する。細部は省いてよいが、省いたことはズームイン候補で示す
- 判断や評価（良い・悪い）より、構造の記述を優先する。読み手が自分で判断できる材料を出す
