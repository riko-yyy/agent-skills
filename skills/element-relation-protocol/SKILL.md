# 要素・関係・プロトコルでキャッチアップする

コードを含む文書群（リポジトリ、設計書、README、仕様書、議事録など）を、**要素・関係・プロトコル**の3つに分解して、理解する側のメンタルモデルを素早く作るための手順。

目的は「全部を説明すること」ではなく、**何をどの順で読めば頭に入るか**を示すこと。

## 用語

- **要素**：境界の内側を、外から気にしなくていい単位（モジュール、クラス、サービス、テーブル、チームなど）
- **関係**：要素同士が影響し合っている事実（呼ぶ、渡す、依存する、依頼する）。向きを持つ
- **プロトコル**：関係を成り立たせている約束。何を渡し、何を前提とし、失敗したときどうなるか

## 手順

### 1. 範囲とズームレベルを決める
- 対象の範囲（リポジトリ全体、特定ディレクトリ、文書セットなど）を確認する
- 1枚の図に出す要素は **7個前後まで**。多いときは上位の要素でまとめ、細部は「ズームイン候補」として残す

### 2. 要素を出す
- 境界がはっきりしているもの（ディレクトリ、名前空間、サービス、テーブル群、担当チーム）から拾う
- 各要素に **責務を1行** で付ける
- 根拠（ファイルパスや文書名）を添える

### 3. 関係を出す
- 「AがBを呼ぶ／Bにデータを渡す／Bに依存する」を **向きつき** で列挙する
- 循環や双方向の依存があれば明記する

### 4. プロトコルを出す
関係ごとに次を書く：
- **何を渡すか**（型、メッセージ、ファイル、テーブル）
- **前提**（事前条件、順序、認証、整合性）
- **失敗時**（例外、リトライ、補償、放置）
- **明示 or 暗黙**：根拠（型定義、API仕様、スキーマ、テスト）を `path:line` などで示せるものは「明示」。示せないものは「暗黙」とする。推測で埋めない

### 5. 暗黙のプロトコルを質問に変える
- 「暗黙」と判定したものを、誰かに聞くための具体的な質問にする
  - 例：「OrderService が InventoryAPI を呼んで失敗したとき、注文は取り消されるのか保留なのか？」

### 6. 読む順番を出す
- 原則：**プロトコル → 要素の責務 → 実装**の順
  - 先に読むもの：インタフェース、型定義、API仕様、スキーマ、テスト
  - 後に回すもの：要素の内側の実装
- 具体的なファイル・文書名を、順番つきで5〜10件挙げる

### 7. 理解を確かめる問いを出す
- 「この要素を差し替えたら何が壊れる？」形式の問いを3つ程度
- 答えられればメンタルモデルができている、という自己チェックに使う

## 出力形式

**図（SVG）＋説明**を基本とする。

- **デフォルト**：自己完結した1枚のHTMLファイル（SVGをインラインで埋め込み、説明を同じページに書く）
- **リポジトリに置く場合やユーザーが求めた場合**：`ERP.svg` ＋ `ERP.md`（mdからsvgを参照する）

### 図のルール
- 要素 = 角丸の箱。箱の中に名前と責務1行
- 関係 = 矢印（向きは依存・呼び出しの方向）
- 矢印のラベル = プロトコル名（例：`POST /orders`, `IRepository<T>`, `orders テーブル`）
- **明示のプロトコルは実線、暗黙のプロトコルは破線**
- ズームイン候補の要素は二重枠など見分けられる印をつける
- 色は意味のあるもの（明示/暗黙）だけに使い、装飾に使わない

### 説明のセクション構成
1. **ひとことで**：この範囲が何をしているかを2〜3文で
2. **要素表**：要素 / 責務 / 根拠
3. **関係とプロトコル表**：from → to / 何を渡すか / 前提 / 失敗時 / 明示・暗黙（根拠）
4. **読む順番**：番号つきリスト
5. **聞くことリスト**：暗黙のプロトコルから作った質問
6. **理解チェック**：差し替えたら何が壊れるか、の問い
7. **ズームイン候補**：次に分解するとよい要素

## 注意
- 根拠を示せないことを断定しない。わからない箇所は「暗黙」か「不明」と書き、質問リストに回す
- 網羅より見通しを優先する。細部は省いてよいが、省いたことはズームイン候補で示す
- 対象がコード以外（チーム構成、業務フロー）でも同じ手順を使う。要素はチームや部署、プロトコルは依頼の流し方・受け入れ条件・契約になる
