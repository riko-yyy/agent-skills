# 要素・関係・プロトコルでキャッチアップする

コードを含む文書群（リポジトリ、設計書、README、仕様書、議事録など）を、**要素・関係・プロトコル**の3つに分解して、理解する側のメンタルモデルを素早く作るための手順。

目的は「全部を説明すること」ではなく、**何をどの順で読めば頭に入るか**を示すこと。読み手は初めてその対象に触る人なので、網羅より見通しを、断定より根拠を優先する。

## 用語

- **要素**：境界の内側を、外から気にしなくていい単位（モジュール、クラス、サービス、テーブル、チームなど）
- **関係**：要素同士が影響し合っている事実（呼ぶ、渡す、依存する、依頼する）。向きを持つ
- **プロトコル**：関係を成り立たせている約束。何を渡し、何を前提とし、失敗したときどうなるか

プロトコルが中心になる理由：要素の内側（実装）は後から読めばよいが、要素同士の約束を知らないと、どこを触ると何が壊れるかが読めない。キャッチアップで最初に効くのはプロトコル。

## 手順

### 1. 範囲とズームレベルを決める
- 対象の範囲（リポジトリ全体、特定ディレクトリ、文書セットなど）を確認する
- メインの図に出す要素は **7個前後まで**。人が一度に見渡せる数に収めるため。多いときは上位の要素でまとめ、細部は「ズームイン候補」として残す

### 2. 要素を出す
- 境界がはっきりしているもの（ディレクトリ、名前空間、サービス、テーブル群、担当チーム）から拾う
- 各要素に **責務を1行** で付け、根拠（ファイルパスや文書名）を添える

### 3. 関係を出す
- 「AがBを呼ぶ／Bにデータを渡す／Bに依存する」を **向きつき** で列挙する
- 循環や双方向の依存があれば明記する

### 4. プロトコルを出す
関係ごとに次を書く：
- **何を渡すか**（型、メッセージ、ファイル、テーブル）
- **前提**（事前条件、順序、認証、整合性）
- **失敗時**（例外、リトライ、補償、放置）
- **明示 or 暗黙**：根拠（型定義、API仕様、スキーマ、テスト）を `path:line` で示せるものは「明示」。示せないものは「暗黙」。推測で埋めると読み手が誤ったモデルを持つので、わからないものは暗黙として残す

### 5. 暗黙のプロトコルを質問に変える
- 「暗黙」と判定したものを、誰かに聞くための具体的な質問にする
  - 例：「OrderService が InventoryAPI を呼んで失敗したとき、注文は取り消されるのか保留なのか？」

### 6. 読む順番を出す
- 原則：**プロトコル → 要素の責務 → 実装**の順
  - 先に読むもの：README、インタフェース、型定義、API仕様、スキーマ、テスト
  - 後に回すもの：要素の内側の実装
- 具体的なファイル・文書名を、順番つきで5〜10件挙げ、それぞれ「なぜここで読むか」を一言添える

### 7. 理解を確かめる問いを出す
- 「この要素を差し替えたら何が壊れる？」形式の問いを3つ程度
- 答えられればメンタルモデルができている、という自己チェックに使う

## 出力形式

**図（SVG）＋説明**を基本とする。

- **デフォルト**：自己完結した1枚のHTMLファイル（SVGをインラインで埋め込み、説明を同じページに書く）。ファイル名は `ERP.html`
- **リポジトリに置く場合やユーザーが求めた場合**：`ERP.svg` ＋ `ERP.md`（mdから相対パスでsvgを参照する）

### メインの図
要素・関係・プロトコルを1枚に描いた図。全体を見渡すための図なので、1枚に収める。

- 要素 = 角丸の箱。箱の中に名前と責務1行
- 関係 = 矢印（向きは依存・呼び出しの方向）
- 矢印のラベル = プロトコル名（例：`POST /orders`, `IRepository<T>`, `find / save`）。関数ならシグネチャを短く書くと読み手が型を追わずに済む
- **明示のプロトコルは実線、暗黙のプロトコルは破線**。色も分ける（例：明示=青、暗黙=橙）。明示の関係に付随する暗黙の前提は、その矢印の近くに橙の短い注記で書く
- ズームイン候補の要素は二重枠、対象の外にあるもの（未実装・別リポジトリ）は破線枠やグレーで区別する
- **凡例を必ず図の中に入れる**。図は説明から切り離されて共有されることが多く、凡例がないと実線と破線の意味が伝わらない
- **フォントはゴシック体を指定する**。指定しないと環境によって明朝体で描画され、小さい文字が読みにくくなる。例：`font-family="'Noto Sans CJK JP','Hiragino Sans','Yu Gothic','Meiryo',sans-serif"`
- 色は意味のあるもの（明示/暗黙/対象外）だけに使い、装飾に使わない
- **図に書くのは名前・責務1行・プロトコル名・短い注記まで**。不変条件の一覧、失敗コードの一覧、根拠の行番号などは説明側の表に回す。図に文字を詰めると、見渡すための図が読むための図になり、スマホでは判読できなくなる。箱の中は3行以内を目安にする
- 読む順番を丸数字で箱に振ると、図と「読む順番」が対応して使いやすい
- 描いたら一度ラスタライズして目視し（`rsvg-convert` やヘッドレスブラウザが使えれば）、ラベルの重なりや見切れを直す

### 補助図（任意）
メインの図だけでは伝わりにくいものがあれば、補助図を足してよい。例：状態遷移（貸出中→返却済）、処理の流れ（シーケンス）、境界値（期限当日は延滞か）。
補助図はメインの図の代わりではなく補足なので、1〜2枚までにし、どのプロトコルを詳しく見るための図かを見出しで示す。svg+md形式なら別ファイル（`ERP-<内容>.svg`）にする。

### 説明のセクション構成
1. **ひとことで**：この範囲が何をしているかを2〜3文で
2. **要素表**：要素 / 責務 / 根拠
3. **関係とプロトコル表**：from → to / 何を渡すか / 前提 / 失敗時 / 明示・暗黙（根拠）
4. **読む順番**：番号つきリスト
5. **聞くことリスト**：暗黙のプロトコルから作った質問
6. **理解チェック**：差し替えたら何が壊れるか、の問い
7. **ズームイン候補**：次に分解するとよい要素

## 注意
- 根拠を示せないことを断定しない。わからない箇所は「暗黙」か「不明」と書き、質問リストに回す
- 網羅より見通しを優先する。細部は省いてよいが、省いたことはズームイン候補で示す
- 対象がコード以外（チーム構成、業務フロー）でも同じ手順を使う。要素はチームや部署、プロトコルは依頼の流し方・受け入れ条件・契約になる
