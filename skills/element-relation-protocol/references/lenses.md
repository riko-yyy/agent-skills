# 対象ごとの読み替え

SKILL.md の手順は共通。ここでは、対象の種類ごとに「何が実行主体で、何がリソースで、どんなプロトコルがあるか」と、見落としやすい点をまとめる。該当する節だけ読めばよい。

## 目次
- コード（アプリ・ライブラリ）
- Claude plugin・エージェント構成
- 文書だけ（設計書・仕様書・ナレッジ）
- パイプライン・CI
- 組織・業務

---

## コード（アプリ・ライブラリ）

- **実行主体**：エントリポイント、ユースケース・サービス、ハンドラ、ジョブ、フック（React の hook など）
- **リソース**：ドメインモデル、データ、DB・テーブル、設定、静的ファイル、外部 API（呼び出し先として）
- **プロトコルの置き場所**：型・インタフェース、関数シグネチャ、スキーマ、テスト、エラー型、API 仕様
- **強さの見分け方**：型やテストで守られる → 強制。コメントや README だけ → 記述。コードはそう動くがどこにも書かれていない（例：IDを振り直さない前提、日付の基準） → 記述（実装のみ）
- **見落としやすい点**
  - 失敗時に気づけない経路（戻り値を見ていない保存、握りつぶされた例外）
  - テスト用の差し替え実装（InMemory など）が本番と違う振る舞いをする箇所
  - 集約や境界が、型ではなく慣習でしか守られていない箇所

## Claude plugin・エージェント構成

- **実行主体**：エージェント（subagent）、hook、slash command、MCP サーバー、スクリプト、そして本体の Claude と人（ユーザー）
- **リソース**：SKILL.md、参照文書（references/）、テンプレート・アセット、設定（plugin.json、settings.json、.mcp.json）、CLAUDE.md・AGENTS.md、出力ファイル
- **関連の種類**
  - 発動：description や条件に合うと Skill が読み込まれる、hook がイベントで動く
  - 呼び出し：エージェントが別のエージェントやスクリプトを起動する、command が Skill を呼ぶ
  - 読み込み：SKILL.md から references を読む指示、CLAUDE.md の import
- **プロトコルの置き場所**：description（発動条件）、frontmatter、hook のイベント名と入出力 JSON、スクリプトの引数と出力形式、ファイルのスキーマ（evals など）、プロンプト内の指示
- **強さの見分け方**：ここが最も重要。プロンプトや SKILL.md の「〜すること」は、守られなくても何も止まらないので **記述**。hook によるブロック、スクリプトの検証、スキーマのバリデーション、権限設定（allow/deny）で守られるものだけが **強制**。「ALWAYS」と書いてあっても強制ではない
- **見落としやすい点**
  - どの description がどの依頼で発動するか（発動条件の重なり・取り合い）
  - エージェント間で受け渡すファイルの形式が、片側にしか書かれていない
  - スクリプトが前提にしている環境（Python、CLI、ネットワーク）
  - 本体の Claude が担う手順と、サブエージェントが担う手順の境目
  - 書く側はスクリプトで形式を守るが、読む側は形式違いを警告だけで通す、といった「片側だけ強制」の受け渡し

## 文書だけ（設計書・仕様書・ナレッジ）

- **実行主体**：文書を書く人・読む人・承認する人、文書が指示しているプロセス（レビュー、リリースなど）。文書だけの対象では人と役割が主な実行主体になるので、対象外の見た目にせず、普通の要素として描く
- **リソース**：文書、章、概念・用語、決定（ADR など）、テンプレート
- **関連の種類**：参照する、前提にする、詳しくする（概要→詳細）、上書きする・置き換える（どちらが新しく、どちらが正か）、書く・承認する（人→文書）
- **プロトコルの置き場所**：用語の定義、文書の優先順位（どれが正本か）、更新のルール（誰がいつ直すか）、テンプレートの書式、ステータス（草案・承認済・廃止）
- **強さの見分け方**：リポジトリの設定やCIで書式・承認が守られる → 強制。文書内のルールだけ → 記述。運用で回っているが書かれていない → 暗黙
- **見落としやすい点**
  - 同じ用語が文書ごとに違う意味で使われている（手順5の「ずれ」の主戦場）
  - 古い文書が廃止されずに残り、どれが正本か分からない
  - 「詳細は〇〇を参照」の参照先が存在しない・古い
  - 同じ判断が複数の文書に書かれていて、正本が決まっていない（手順5の「重複」）
  - 「記述」の中でも、文書同士がリンクで結ばれているか、本文で名前を挙げているだけかで、追いやすさが大きく違う。リンクの有無を表に書く
  - 仕組みで強制されるルールが1つもないことが多い。その場合、図の線はほぼすべて「記述」と「暗黙」になるが、それ自体が「ずれを止める仕組みがない」という発見なので、ひとことでにも書く

## パイプライン・CI

- **実行主体**：ワークフロー、ジョブ、ステップ、ボット、エージェント、人（承認者）
- **リソース**：ブランチ、PR、Issue、ラベル、成果物（ビルド成果・レポート）、シークレット、設定ファイル
- **関連の種類**：イベントで起動する（push、PR merged、schedule）、needs で後続ジョブを動かす、成果物を受け渡す、ラベルやコメントで次の段を動かす
- **プロトコルの置き場所**：トリガー条件（on:、paths、if）、ジョブ間の outputs、ラベル名、ブランチ保護、権限（permissions）
- **強さの見分け方**：ワークフローの条件やブランチ保護で守られる → 強制。README やプロンプトで「ラベルを付けること」と書いてあるだけ → 記述
- **見落としやすい点**
  - 前のジョブの結果（PR番号など）が後ろのジョブに渡っていない
  - 生成物が自分自身のトリガー条件に当たって、ループや再実行が起きる
  - リポジトリの外（GitHub 側の設定）にしかない前提

## 組織・業務

- **実行主体**：チーム、役割、個人、外部の組織
- **リソース**：成果物、チケット、文書、システム、予算・時間
- **関連の種類**：依頼する、引き渡す、承認する、報告する、使う
- **プロトコルの置き場所**：依頼の流し方（チケットのテンプレート、窓口）、受け入れ条件、SLA、会議体、契約、権限
- **強さの見分け方**：ツールや承認フローで強制される → 強制。ルールとして書かれている → 記述。慣習で回っている → 暗黙
- **見落としやすい点**
  - チームの境界とシステムの境界が一致していない（コンウェイの法則）
  - 依頼の窓口が複数あり、どれが正式か曖昧
  - 特定の個人に依存している暗黙の手順
